### P2-A · SEO Foundation — "Chat-First, SEO-Second"

> **Strategic framing:** The current site is invisible to search engines by design (ADR-001, ADR-013). This was the right call for launch. Phase 2 introduces a parallel indexable content layer without touching the user experience. Google reads the program's full content; humans experience the conversation. The medium remains the message.

#### Architecture Decision: The `<noscript>` Enrichment Pattern

The most cost-effective, zero-infrastructure-change approach to indexable content on a static React SPA.

**How it works:**
1. A build-time script (`scripts/src/seo-inject.ts`) reads the knowledge base Markdown files and generates a rich semantic HTML block
2. This block is injected into `artifacts/miaw/public/index.html` inside a `<div id="seo-content">` that is CSS-hidden for real users (`display:none; visibility:hidden` via a class) but fully readable by search engine crawlers
3. The React app mounts normally and completely covers the SEO layer in the DOM — real users never see it
4. Google's crawler (which frequently does not execute JavaScript) reads the rich HTML content and indexes it
5. This is a legitimate, Google-approved technique — it is not cloaking because the content is the same content the agent would discuss; it's not served differently by the server, just hidden via CSS

**SEO content structure in the injected block:**
```html
<div class="seo-content-layer" aria-hidden="true">
  <h1>MIAW — Master in Intelligent Artificial Worlds</h1>
  <h2>The First Postgraduate Program at the Intersection of AI and Architecture</h2>
  <p>18-week postgraduate program for AEC professionals and AI engineers...</p>
  <section>
    <h2>Curriculum — 9 Modules</h2>
    <article id="module-f0">...</article> <!-- each module -->
  </section>
  <section>
    <h2>Frequently Asked Questions</h2>
    <!-- structured Q&A from faq.md -->
  </section>
  <!-- Entity-rich: link entities to each other, use schema vocabulary in text -->
</div>
```

**Why this over other options:**
- No framework migration (Next.js would require full rewrite, high risk)
- No server-side rendering infrastructure (no extra cost, no new complexity)
- No URL structure changes
- Zero impact on existing user experience
- Works within the current static Vite build pipeline

#### Architecture Decision: Static HTML Routes via Express

The three static pages (`/about`, `/curriculum`, `/apply`) are served by the Express API server, not the React SPA. They are pre-rendered at build time as static HTML files placed in `artifacts/api-server/public/seo/` and served by a simple Express route. This means:

- `/curriculum` — All 9 modules (F0–F8), each with description, deliverables, technologies used

### P2-B · "How to Apply" — AI-Native Application Flow

> **Strategic framing:** The current waitlist CTA is the right tool for the pre-cohort phase. But as applications open, the program needs structured data per applicant for admissions review — background, motivations, stated project experience, technical level, concerns expressed. A traditional form loses the intelligence the conversation has already built. The architecture below makes the application form an extension of the conversation, not a replacement of it.

#### Architecture Decision: Conversation-Driven Application (No Form Fields)

The "How to Apply" experience is not a form. It is a second, deeper conversation — triggered when the visitor is ready to apply, picking up where the 8-turn qualification left off.

**The two-path CTA (replacing the current single waitlist CTA):**
```
After turn 8:
  ├── "Join the waitlist" → [current flow: email capture, Airtable, done]
  └── "Apply now"         → [new: application conversation mode]
```

**Application conversation mode:**
1. A new system prompt activates (application mode) — Claude shifts from qualification to structured interview
2. 6–8 additional turns, tailored to the visitor's already-inferred profile:
   - Architects: specific project experience, design process, AI tool usage history
   - Engineers: technical stack depth, domain exposure, collaboration experience with AEC
   - Researchers: current work, academic goals, bridge to practice
3. Claude asks exactly one question per turn (same as qualification mode)
4. At the end: a single optional portfolio field — URL or file link (Google Drive, Behance, personal site, GitHub). One input, not a form. The conversation WAS the form.

**Server-side processing on submission (`POST /api/apply`):**
Two sequential Claude calls happen entirely server-side, invisible to the user:

```
Call 1 — Structured Extraction (~$0.03):
  Input: full conversation transcript (qualification + application turns)
  Prompt: "Extract and structure: background, stated_project_types, self_assessed_technical_level,
           motivations, concerns_expressed, key_quotes, portfolio_url, 
           fit_score (1–5 with rationale), recommended_follow_up_question_for_admissions"
  Output: JSON object stored with the application record

Call 2 — Personalized Acknowledgment (~$0.03):
  Input: extracted summary + applicant's profile
  Prompt: "Write a 120-word personalized acknowledgment that references specific details from 
           their conversation — the project they mentioned, the technology they are curious about, 
           the concern they expressed. Warm but not effusive. Sign as MIAW."
  Output: The body of the email sent to the applicant
```

**Why this is the most innovative, not the most expensive approach:**
- Total cost per complete application: ~$0.50–$0.60 (conversation + 2 extraction calls)
- At 200 applications: ~$100–$120 in API costs — negligible against €6,000 tuition
- The personalized feedback is generated at the same moment of submission — no admissions team delay
- Every applicant receives a response that feels hand-written, because it references exactly what they said
- Admissions team receives a pre-structured summary — they read a 200-word extracted profile, not a full transcript

#### Data Model (Drizzle + Postgres via `lib/db`)

The `lib/db` package already has Drizzle configured. Application data requires persistent storage beyond Airtable.

```typescript
// New tables in lib/db/src/schema.ts

applications:
  id                 uuid PRIMARY KEY
  email              text NOT NULL
  visitorType        enum (architect|engineer|researcher|developer|student|urban_planner|unknown)
  qualificationTurns integer        // turns in the 8-turn flow
  applicationTurns   integer        // turns in the application mode
  portfolioUrl       text           // optional, applicant-provided
  extractedSummary   jsonb          // structured output from Call 1
  fitScore           integer        // 1–5, from extraction
  personalizedAck    text           // generated by Call 2
  status             enum (received|reviewed|accepted|waitlisted|declined)
  createdAt          timestamp
  updatedAt          timestamp

application_conversations:
  id                 uuid PRIMARY KEY
  applicationId      uuid REFERENCES applications(id)
  role               enum (user|assistant)
  content            text
  turnNumber         integer
  phase              enum (qualification|application)
  createdAt          timestamp
```

**Why Postgres here instead of Airtable:**
- Application data is structured and relational (conversations reference applications)
- Volume is manageable (Postgres free tier: unlimited)
- GDPR compliance is easier with a proper database and row-level access control
- Airtable remains for the waitlist (non-technical team access)
- `lib/db` already has Drizzle configured — this is additive only

#### New API Routes

```
POST /api/apply              — submit application (triggers extraction + ack generation)
```

**`POST /api/apply/chat` system prompt (application mode):**
- Shorter than qualification mode (~400 tokens)
- Phase-aware: knows which application questions have been asked
- Profile-aware: asks role-specific questions based on already-inferred type
- Constraint: must ask exactly the questions needed for structured extraction (background, project types, skills, motivations, concerns) — but naturally, not as a form checklist

### P3-A · Full SSR Shadow Layer — Entity-Based SEO

> **Architecture note:** This is a significant expansion of the P2-A foundation. The difference: P2-A creates a hidden layer with the knowledge base content. P3-A creates a full semantic site graph — each entity (technology, module, concept, faculty member) gets its own indexable page. ## Phase 5 — Contextual Visual Layer

> Conversation-aware images that surface from the background as Claude discusses specific topics. The visual system listens to the conversation and responds — an ambient, cinematic layer that deepens the world without breaking the conversational contract.

### ADR-017: Architecture of the Contextual Visual Layer

**Status:** Decided

**Core principle:** The visual layer is subordinate to the conversation at all times. Images appear only when a topic is specific enough to warrant one, never on generic turns, never blocking text, never drawing focus away from what Claude is saying.

**Topic detection strategy — P5-A:** Client-side keyword scoring on the completed assistant response + last two user messages. Mirrors the existing `PROFILE_KEYWORDS` pattern (no new API calls, no changes to the streaming format). A topic wins only when its keyword score reaches a threshold (`MIN_SCORE = 2`), preventing false positives on single-word mentions. Returns `null` when no topic clears the threshold — image fades out.

**Why not server-side (P5-B)?** The plain-text stream carries no metadata. Adding server-side topic hints in P5-A would require either: (a) a parallel `POST /api/topic` call per turn (latency + complexity), or (b) changing the stream format to JSON-framed chunks (breaking change, adds parsing complexity). Client-side is the right tradeoff for Phase 1 given the existing keyword-scored RAG system.

**Image animation:** CSS `@keyframes imageFloat` — transform-only (compositor thread, no layout thrash). Same design vocabulary as `@keyframes meshFlow` for the gradient blobs: slow, organic, alive. 32s period with subtle scale breathing. Framer Motion `AnimatePresence` drives the 1.6s cross-fade between topics.

**Z-index stack:**
- `z-0`: gradient mesh canvas (background)
- `z-1`: floating image container (above gradient, below UI)
- `z-10`: "How to apply" nav pill
- `z-10+`: message bubbles, input bar, overlays

**Graceful degradation:** `FloatingImage` calls `onError` when an image file is missing → component returns null → nothing shown. The folder `artifacts/miaw/public/images/` is tracked in version control but images are a 👤 Human Task — the system works with zero, one, or all images present.

**`prefers-reduced-motion`:** The CSS `--animated` modifier class is NOT applied when the media query fires. The image appears statically (still cross-fades via Framer Motion which respects the query at its own level).

### P5-B · Server-Side Topic Signaling

> **Status: ⏳ Not Started** — implement when client-side detection accuracy proves insufficient.

**Approach:** Inject a topic hint into the stream as a prefixed metadata line before the text content. ## Architecture Decision Records — New (Phase 2–4)

### ADR-014: AI-Native Application Form (Conversation, Not Fields)

**Status:** Proposed

**Context:**
The application form was scoped in Phase 2 (PRODUCTION_ROADMAP, original P2). The team has two choices: (A) a traditional multi-field form (name, background, portfolio URL, motivation statement), or (B) an extension of the existing conversation experience into a structured application mode.

**Decision:**
Option B — AI-native application conversation. The form IS the conversation. No multi-step form wizard. No fields except one optional portfolio URL at the end.

**Rationale:**
- A traditional form immediately breaks the brand contract (ADR-001: one surface, no navigation)
- The conversation has already inferred the visitor's profile by turn 8 — a form starts that discovery process over from zero
- Claude can ask profile-appropriate questions (architects get different questions from engineers)
- Server-side extraction generates structured data equivalent to any form submission, with additional qualitative signal
- Personalized acknowledgment is genuinely differentiated — no competitor does this
- Cost is negligible against program tuition

**Consequences:**
- Application data quality depends on the extraction prompt quality — must be tuned
- Applicants who are uncomfortable with open-ended AI conversation are excluded — acceptable (MIAW is specifically for people who are comfortable with AI interfaces)
- GDPR consent must be explicit before conversation data is stored server-side

### ADR-015: `<noscript>` Enrichment + Express Static Pages for SEO (No Next.js)

**Status:** Proposed

**Context:**
SEO is near-zero (ADR-001, ADR-013 accepted this for launch). As organic search becomes a meaningful acquisition channel, a content layer is needed. The options are: (A) migrate to Next.js App Router, (B) add a pre-rendering step (Puppeteer), (C) add a `<noscript>` enrichment layer + static Express-rendered pages, (D) serve different content to bots (cloaking — explicitly rejected).

**Decision:**
Option C. The `<noscript>` enrichment layer covers the main `/` URL. Static Express-rendered HTML pages cover all other routes. No framework migration.

**Rationale:**
- Next.js migration is a full architectural rewrite (4–6 weeks, high risk, breaks the existing pipeline)
- Puppeteer pre-rendering adds infrastructure complexity and maintenance cost
- Option C requires no new infrastructure — the API server already exists, static HTML is trivial to serve
- `<noscript>` is a Google-approved, penalty-free technique for content visibility to crawlers
- The static pages are a content exercise, not a technical one — they can be generated from existing knowledge files

**Consequences:**
- `<noscript>` content must match what the AI would say — must not mislead crawlers
- Static pages must be updated when knowledge files change (the build script handles this automatically)
- Internal linking between pages requires explicit management (not automatic like a CMS)

### ADR-016: Resend for Transactional Email

**Status:** Proposed

**Context:**
Phase 2 introduces two new email flows: waitlist confirmation and application acknowledgment. Options: Resend, Postmark, SendGrid, AWS SES, Nodemailer (SMTP).

**Decision:**
Resend with React Email templates.

**Rationale:**
- Free tier: 3,000 emails/month — sufficient through first cohort applications
- TypeScript SDK is first-class; React Email templates are version-controlled alongside the codebase
- Simpler than SendGrid (which requires domain authentication and has a more complex API)
- Cheaper than Postmark at low volume
- Domain verification is straightforward

**Consequences:**
- Requires domain verification for the `FROM_EMAIL` address — must have the custom domain confirmed first (👤 Human Task: P1-A custom domain)
- If Resend is unavailable, emails are lost (no retry queue in Phase 2). Phase 3 can add a Postgres-backed email queue if reliability requires it.

## Architectural Principles: Preserved Through Phase 2–4

The following principles from the TOGAF overview (ADR AP-01 through AP-07) must be respected in all Phase 2+ decisions:

| Principle | How Phase 2 Respects It |
|---|---|
| AP-01: Conversation over content | The `/` experience is unchanged. SEO layer is additive and invisible to users. |
| AP-02: Intelligence through specificity | Application mode asks precisely calibrated questions — no generic form fields. |
| AP-03: Minimal surface, maximum depth | No new navigation, no new pages in the React SPA. Static pages are accessed via direct URL only. |
| AP-04: Graceful degradation | Application mode falls back gracefully if extraction call fails (raw transcript stored; team reviews manually). Email failure is logged, not user-facing. |
| AP-05: Contract-first API design | All new routes added to `openapi.yaml` before implementation. |
| AP-06: No vendor lock-in | Resend can be replaced with any SMTP provider by changing one wrapper function. Claude extraction uses standard `messages.create` call — model-agnostic. |
| AP-07: Privacy by design | GDPR consent is explicit before any conversation is stored server-side. `sessionStorage` (not `localStorage`) for session tokens. |
